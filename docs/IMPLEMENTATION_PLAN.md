# SPOMover — план реалізації

Перелік функціоналу з ідентифікаторами (MAP-*, INV-*, PLN-*, EXE-*, LCK-* тощо) — у [FEATURES.md](FEATURES.md).

Стан на 09.11.2026: **етапи 0–6 виконано** (пілот — власник; EXE-7, перевірка цільових бібліотек, звіт пілоту), версія 0.6.0. Працюють: інвентаризація джерела й цільових бібліотек (повна і лише змінами), мапінг з перевіркою покриття, план пакетів із хвилями, прогнозом і порівнянням знімків, переміщення `apply` засобами SharePoint (MoveCopyUtil) з повторами, відкладенням заблокованих файлів і звіркою після збоїв, `verify`, `retry`, експорт правил для SPOReplaceLink. Усе перевірено на `fs-test`: 3 233 справжні файли переміщено туди й назад без помилок ([API_SPIKE.md](API_SPIKE.md), розділ 4). Переміщення змінює вміст документів Office (п. 39) — власник прийняв. Файли, відкриті на редагування, перевірено (пп. 40–42). План і переміщення доступні й у вікні застосунку (етап 5). Етап 6 — пілот — проведено власником. Віддалений репозиторій `upstream` вказує на SPOReplaceLink: виправлення інфраструктури звідти переносяться через `git cherry-pick`.

## 1. Архітектура

```
 ┌──────────── SPOMover.exe (десктопний застосунок, сесія користувача) ─────────────┐
 │  Вікно WPF + WebView2: дашборд, мапінг, план, пакети, файли, помилки (Blazor)     │
 │  Engine: інвентаризація, планувальник, виконавець хвиль, повтори, пауза           │
 │    └─ Spo: MSAL, бюджет RU, throttling                                            │
 │         ├─ Graph: delta-перелік, створення папок, перелік залишків                │
 │         └─ SharePoint REST: CreateCopyJobs, GetCopyJobProgress, MoveCopyUtil,     │
 │                             check-out (CheckoutUser, GetCheckedOutFiles)          │
 │  State: SQLite (інвентаризація, мапінг, план, пакети, файли, спроби)              │
 │  Локальний REST API (localhost) ◄── CLI (розклад, автоматизація)                  │
 └───────────────────────────────────────────────────────────────────────────────────┘
```

Ключові рішення:
- **Архітектура SPOReplaceLink без змін:** один десктопний застосунок, рушій не залежить від вікна, CLI — тонкий клієнт до локального API, налаштування в GUI з JSON-експортом.
- **Переміщення виконує SharePoint.** Інструмент не передає вміст файлів, тому мережа машини і пам'ять не обмежують швидкість. Обмеження — throttling і швидкість виконання завдань на боці SharePoint.
- **Graph для читання, REST для переміщення.** Graph не переміщує елементи між бібліотеками (drives), тому переміщення — через SharePoint REST. Обидва клієнти ділять один бюджет RU і стан throttling.
- **Одиниця роботи — пакет**, а не файл: папка цілком або набір файлів однієї папки. Стан окремих файлів відновлюється з журналу завдання і звірки, тому звіти все одно поштучні.
- **Ідентифікатор завдання записується до продовження роботи.** Після падіння рушій спершу опитує стан уже запущених завдань, а не запускає їх повторно (EXE-8).

## 2. Що береться з SPOReplaceLink

| Проєкт | Рішення | Що змінюється |
|---|---|---|
| `Core` | Залишається частково | `Urls` (нормалізація шляхів) і `Config` — так; `Rules` перетворюється на модель мапінгу; `Processing` (результат обробки файлу) прибирається |
| `OpenXml` | Видаляється | Лише `SimpleXlsxReader` переноситься в `Core` для імпорту мапінгу з XLSX |
| `ExcelWorker` | Видаляється | — |
| `Spo` | Залишається | Додається `SpoRestClient` (токен на ресурс `https://<tenant>.sharepoint.com`), спільний з `GraphClient` облік RU і повтори рівня 1 |
| `State` | Залишається механізм | Нова схема: `inventory_items`, `folders` (агрегати), `mappings`, `plans`, `batches`, `items`, `attempts` |
| `Engine` | Переписується | Зберігаються життєвий цикл прогону, пауза/продовження/зупинка, черги повторів, метрики; конвеєр файлу замінюється конвеєром пакета |
| `Host`, `Cli` | Залишаються | Нові команди: `inventory`, `plan`, `apply`, `verify`, `retry`, `map test`, `export-rules`; команда `local` прибирається |
| `Ui`, `Desktop` | Залишаються каркас і загальні компоненти | Нові сторінки: мапінг, план, пакети; профіль без вкладок Excel і місць заміни |
| `installer` | Без змін | UpgradeCode уже новий, щоб інсталятор не оновлював SPOReplaceLink |
| `tests/Shared/FakeGraph` | Розширюється | Емулятор SharePoint: бібліотеки одного сайту, завдання переміщення, блокування, часткові невдачі, throttling |
| `tools/DemoSeed` | Переписується | Демо-сайт з деревом папок і мапінгом |

## 3. Технічний стек

Як у SPOReplaceLink: .NET 10, ASP.NET Core (Kestrel), WPF + BlazorWebView + MudBlazor, System.CommandLine, MSAL.NET, `HttpClient` з власним циклом повторів, SQLite (WAL), Serilog, xUnit + bUnit. Excel COM і обробка zip/XML більше не потрібні.

## 4. Конвеєр одного пакета

```
pending
  │ перевірка: джерело на місці, у цілі немає конфлікту імен (EXE-4)
  │ за потреби — створення цільових папок (EXE-3)
  ▼
submitted                 ← MoveFolderByPath: синхронний запит (основний шлях);
  │                           CreateCopyJobs: jobId записується в базу одразу, далі опитування GetCopyJobProgress
  ▼
completed ─────────────────────────────┐
partial  → залишки в джерелі            │
           → пакети рівня файлу (EXE-5) │
failed   → клас помилки → повтори       │
                                        ▼
                                    verified   ← звірка: усі файли в цілі, джерело порожнє
```

Після перезапуску пакети в `submitted` спершу перевіряються: CreateCopyJobs — опитуванням за jobId, MoveFolderByPath (відповідь могла загубитися) — одразу звіркою. Якщо завдання вже не знайдено, стан визначається звіркою джерела і цілі, а не повторним запуском.

## 5. Етапи

Тривалість — орієнтовна, для однієї людини з Claude Code.

### Етап 0. Перевірка API на тестовому сайті (2–3 дні) — до написання виконавця

Мета — зняти найбільші невідомі, від яких залежить дизайн виконавця.

1. В реєстрації застосунку в Entra додати дозвіл **SharePoint → Application → Sites.Selected** і надати згоду адміністратора. Доступ до тестового сайту видати рівнем `write`.
2. Скрипт генерації тестової структури: 3 бібліотеки, ~20 тис. файлів, глибина до 8, папки на 5–10 тис. файлів, кирилиця і пробіли в іменах, довгі шляхи.
3. Перевірити і записати в [FEATURES.md](FEATURES.md), розділ 16:
   - `CreateCopyJobs` у режимі move між бібліотеками одного сайту: формат журналу, швидкість на 1, 5, 10 тис. файлів, чи зберігаються Created/Author і з `RetainEditorAndModifiedOnMove` — Modified/Editor;
   - поведінка при частковій невдачі переміщення папки: що лишається в джерелі, чи створюється папка в цілі;
   - файл, відкритий у Word/Excel (спільне редагування), з `BypassSharedLock` і без; що бачить користувач;
   - файл на check-out і файл без опублікованої версії;
   - конфлікт імен у цілі з `KeepBoth = false`;
   - вартість у RU і заголовки throttling на запити REST;
   - скільки живе завдання в `GetCopyJobProgress` після завершення (для EXE-8).

Результат — короткий звіт у `docs/API_SPIKE.md` і рішення по параметрах за замовчуванням.

1. Видалити `OpenXml`, `ExcelWorker` і їхні тести; `SimpleXlsxReader` — у `Core`.

Критерій: рішення збирається, усі тести інфраструктури (Spo, Host, загальні компоненти UI) зелені, застосунок відкривається з порожніми розділами.

### Етап 2. Мапінг та інвентаризація (5–7 днів)

1. Модель мапінгу, пошук правила за найдовшим збігом (MAP-1…MAP-3), валідація (MAP-4), імпорт і експорт (MAP-6), `map test` (MAP-7).
2. Схема бази для інвентаризації; delta-перелік з продовженням (INV-1); агрегати папок одним SQL-проходом після переліку (INV-2).
3. Check-out і файли без опублікованої версії через REST (INV-3); інвентаризація цілей (INV-4); оновлення за delta-токеном (INV-5).
4. Звіти інвентаризації і покриття мапінгу (INV-6, MAP-5).
5. Тести: модульні на мапінг; синтетична інвентаризація 2 млн записів — час і розмір бази (NFR-2).

**Виконано (06.11.2026).** 167 тестів зелені, самоперевірка застосунку на демо-даних — `RESULT ok`. Що зроблено і що інакше, ніж заплановано:

- **Профіль:** `source` (сайт, бібліотека, папка), `targetLibraries` (назви на тому самому сайті), `mapping`. Прогін перелічує джерело (індекс 0) і цільові бібліотеки (1…n). Помилки мапінгу не блокують інвентаризацію (`ProfileValidation.IsValidForInventory`): вона потрібна, щоб мапінг довести до ладу.
- **Мапінг** (`Core/Mapping`): порожній `path` — той самий шлях, що в джерелі; `/` — корінь; бібліотека `-` — «лишити в джерелі». Для правила на файл `path` — повний новий шлях з ім'ям.
- **INV-2:** агрегати папок рахуються в рушії (C#, один прохід по файлах бібліотеки), а не SQL-запитом — так простіше врахувати порожні папки й обмеження `source.folder`. Таблиця `folder_stats`.
- **INV-3:** файли на check-out — з delta (`$select=…,publication`: `level` і `checkedOutBy`), без окремого проходу; так вирішено після етапу 0 (результат 16), спершу був REST-перелік усіх елементів за ID. Через SharePoint REST (той самий конвеєр запитів, що й Graph: бюджет RU, Retry-After, оновлення токена; токен на `https://<тенант>.sharepoint.com/.default`) лишився лише `POST GetCheckedOutFiles()` — файли без опублікованої версії. З роллю `write` він дає 403 (результат 18), тож крок пропускається з приміткою прогону (`run_notes`). Перевірено на `fs-test` 08.11.2026: інвентаризація 65 048 файлів (55,6 ГБ) за 2 хв 21 с, без throttling.
- **MAP-5:** `MappingCheck` застосовує мапінг до останньої інвентаризації того самого джерела і зберігає результат по кожному файлу (`mapping_preview`) для звітів; конфлікти — SQL-запитом з явним порядком з'єднань (корельований підзапит давав 69 с на 10 тис. файлів, тепер мілісекунди). 100 тис. файлів джерела — 1,3 с.
- **INV-5 (оновлення за delta-токеном) перенесено на етап 3:** воно потрібне перед хвилями і разом із перебудовою плану (PLN-4); повторна інвентаризація поки повна. Для перейменованих папок delta не повертає вкладені файли — шляхи доведеться перераховувати від дерева папок.
- **Попутно:** лічильник «Знайдено» більше не рахує `COUNT(*)` після кожної сторінки переліку (на мільйоні файлів це додало б хвилини); точне число — наприкінці кожної бібліотеки.
- **Не зроблено з плану:** синтетичний тест на 2 млн записів — є на 200 тис. (GUI, перевірка покриття); повний обсяг перевіряється пілотом.

## 7. Порядок бойового прогону

1. `inventory` → звіт; розсилка власникам файлів на check-out; прохання відключити синхронізацію OneDrive для бібліотеки.
2. Створення цільових бібліотек з тими самими колонками і типами вмісту.
3. Мапінг → `plan` → погодження плану і хвиль.
4. Пілотна хвиля → `verify` → перевірка користувачами.
5. Для кожної наступної хвилі, у неробочий час:
   - бібліотека-джерело стає доступною лише для читання (вручну до реалізації LCK-4);
   - оновлення інвентаризації і плану хвилі (INV-5, PLN-4);
   - `apply` → відкладені хвилі для заблокованих → `verify`;
   - дозволи відновлюються.
6. Розбір «потребують уваги»: конфлікти, check-out, задовгі шляхи → повтор або «ігнорувати з коментарем».
7. `export-rules` → прогін SPOReplaceLink по нових бібліотеках для виправлення зв'язків між Excel-файлами.
8. Фінальний звіт, архівування бази стану.

Відкат — зворотний мапінг (ціль → джерело) і той самий інструмент. Звіт по файлах (REP-2) містить старий і новий шлях кожного файлу.

## 8. Ризики

| Ризик | Вплив | Як зменшити |
|---|---|---|
| Поведінка Copy/Move API відрізняється від очікуваної (журнал, часткові невдачі, блокування) | Переробка виконавця | Етап 0 до написання виконавця |
| Користувачі працюють з файлами під час хвилі | Заблоковані файли, залишки | Заморозка джерела, неробочий час, відкладені хвилі, `BypassSharedLock` |
| Throttling на великому обсязі | Повільніші хвилі | Бюджет RU, вікна роботи, прогноз з пілоту |
| Помилка в мапінгу | Файли не там | Валідація, звіт покриття, погодження плану, `map test`; відкат зворотним мапінгом |
| Синхронізація OneDrive у користувачів | Масове видалення і завантаження на клієнтах, скарги | Розсилка до старту, хвилі |
| Зв'язки між Excel-файлами | Биті посилання після переміщення | MAP-8 + SPOReplaceLink |
| Вкладки Teams, потоки, ярлики на старі шляхи | Ламаються | Інвентаризація залежностей власниками, комунікація |
| Розбіжність з SPOReplaceLink | Виправлення інфраструктури треба переносити вручну | `upstream` + `cherry-pick`; інфраструктуру не змінювати без потреби |
