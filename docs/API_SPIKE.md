# Перевірка Copy/Move API (етап 0)

> **Примітка.** Утиліту `tools/SPOMover.ApiSpike` і сирі відповіді API (`docs/api-spike/`) з тестового тенанта не включено до публічного репозиторію; нижче лишено опис кроків і висновки.

Утиліта `tools/SPOMover.ApiSpike` (`spo-mover-spike`) перевіряє на **тестовому** сайті, як насправді поводиться SharePoint Copy/Move API (`Site.CreateCopyJobs` / `GetCopyJobProgress`), і записує звіт. Від результатів залежить дизайн виконавця (FEATURES, розділи 6, 7, 9; IMPLEMENTATION_PLAN, етап 0).

Утиліта змінює дані тестового сайту: створює папку `SpikeRun-<час>` у двох бібліотеках, переміщує, бере файли на check-out. **Не запускайте її на робочому сайті.**

Код утиліти написано без доступу до тенанта; жодну з перевірок проти SharePoint ще не виконано. Те, що утиліта пише у звіт, — це перші реальні дані.

## 1. Підготовка

### 1.1. Тестовий сайт і бібліотеки

1. Окремий сайт, наприклад `https://contoso.sharepoint.com/sites/spomover-test`.
2. Дві бібліотеки документів на ньому:
   - джерело — можна стандартну «Documents» («Документи»);
   - ціль — нова бібліотека, наприклад `SpikeTarget`.
3. Бажано, щоб у бібліотеках було ввімкнено журнал версій (за замовчуванням так) і не вимагався check-out.

### 1.2. Доступ застосунку

Той самий застосунок Entra і сертифікат, що й для SPOMover ([USER_GUIDE](USER_GUIDE.uk.md), 1.5). Окрім Graph `Sites.Selected` потрібно:

1. Entra → застосунок → **API permissions** → **Add a permission** → **SharePoint** → **Application permissions** → **Sites.Selected** → **Add**.
2. **Grant admin consent for …** — статус «Granted».
3. Доступ до тестового сайту з роллю **`write`** — так само, як у USER_GUIDE 1.5, крок 3 (Graph Explorer, `POST /sites/{id}/permissions` з `"roles": ["write"]`). Цей доступ діє і для Graph, і для SharePoint REST.

Без дозволу SharePoint утиліта отримає токен, але SharePoint REST відповість `401`/`403`. Крок `access` скаже про це прямо, а кроки, що потребують REST, буде пропущено з цією причиною.

### 1.3. Підключення

Файл підключення у форматі SPOMover (як `samples/connection.example.json`), `authMode` — `certificate`:

```json
{
  "name": "spo-mover-1",
  "tenantId": "contoso.onmicrosoft.com",
  "clientId": "<Client ID застосунку>",
  "authMode": "certificate",
  "certificateThumbprint": "<відбиток>",
  "certificateStore": "CurrentUser"
}
```

Потрібен .NET SDK 10 на машині, де лежить сертифікат.

## 2. Запуск

З кореня репозиторію. Повний прогін (усі кроки, крім очищення; наприкінці утиліта спитає, чи видалити створене):

```bash
dotnet run --project tools/SPOMover.ApiSpike -- --connection conn.json --site https://contoso.sharepoint.com/sites/spomover-test --source "Documents" --target "SpikeTarget"
```

Окремі кроки з тією самою папкою звіту (стан зберігається в `state.json`, тож кроки можна запускати в різні дні):

```bash
dotnet run --project tools/SPOMover.ApiSpike -- --connection conn.json --site https://contoso.sharepoint.com/sites/spomover-test --source "Documents" --target "SpikeTarget" --out spike-1 --step seed,move-folder
```

```bash
dotnet run --project tools/SPOMover.ApiSpike -- --connection conn.json --site https://contoso.sharepoint.com/sites/spomover-test --source "Documents" --target "SpikeTarget" --out spike-1 --step job-lifetime --quick
```

Швидкість на 1, 5, 10 тис. файлів — окремий запуск на кожен розмір, кожен зі своїм `--out`:

```bash
dotnet run --project tools/SPOMover.ApiSpike -- --connection conn.json --site https://contoso.sharepoint.com/sites/spomover-test --source "Documents" --target "SpikeTarget" --out spike-5000 --files 5000 --step seed,move-folder,cleanup
```

Видалення всього створеного (у кошик сайту, після підтвердження):

```bash
dotnet run --project tools/SPOMover.ApiSpike -- --connection conn.json --site https://contoso.sharepoint.com/sites/spomover-test --source "Documents" --target "SpikeTarget" --out spike-1 --step cleanup
```

Самоперевірка без SharePoint:

```bash
dotnet run --project tools/SPOMover.ApiSpike -- --selftest
```

Параметри:

| Параметр | Що задає |
|---|---|
| `--connection` | Файл підключення (1.3). |
| `--site` | Тестовий сайт. |
| `--source`, `--target` | Дві різні бібліотеки сайту: назва, як у SharePoint, або URL-назва (`Shared Documents`). |
| `--out` | Папка звіту, за замовчуванням `spike-<час>`. |
| `--step` | Кроки через кому або кілька разів: `access`, `seed`, `move-folder`, `partial`, `shared-lock`, `conflict`, `job-lifetime`, `checkout-scan`, `cleanup`. |
| `--files N` | Файлів у папці для переміщення, за замовчуванням 200. |
| `--quick` | `job-lifetime`: опитування через 0, 10, 30, 60 с замість 0, 1, 5, 15 хв; ліміт очікування завдання 15 хв замість 45. |

Ручні дії (кроки `move-folder` і `shared-lock`) утиліта описує в консолі й чекає Enter; «пропустити» + Enter — пропуск дії. Ctrl+C зупиняє прогін, звіт зберігається.

### Що надіслати

Після запуску утиліта показує папку звіту. Її треба заархівувати цілком і надіслати:

```powershell
Compress-Archive -Path .\spike-1 -DestinationPath .\spike-1.zip
```

Вміст папки:

| Файл | Що містить |
|---|---|
| `report.md` | Звіт українською: по кожному кроку — що зроблено, результат, час, висновки «так / ні / невідомо» з доказами. |
| `requests.jsonl` | Кожен HTTP-запит і відповідь: метод, URL, код, тривалість, `request-id` / `SPRequestGuid`, заголовки throttling (`RateLimit-*`, `x-ms-*`, `Retry-After`), тіло. Заголовок `Authorization` і токени не записуються. |
| `raw/` | Тіла запитів і відповідей `CreateCopyJobs`, кожне опитування `GetCopyJobProgress`, журнали завдань (`*-logs.jsonl`: кожен запис і як рядок, і розібраний JSON), поля файлів до і після, claims токенів (без підпису). |
| `state.json` | Що створено (для повторних кроків і очищення). |

У файлах є адреси сайту, імена файлів, ім'я й пошта користувача, що завантажив файли вручну. Паролів, ключів і токенів немає.

## 3. Кроки і навіщо вони виконавцю

Кожен SharePoint-запит: `User-Agent: NONISV|SPOMover|SPOMover-ApiSpike/0.1`, на `429`/`503` — пауза за `Retry-After` (або 5, 10, 20… с) і до 6 спроб, на `401` — одне примусове оновлення токена. Невдача одного кроку не зупиняє інші.

Усі переміщення — `POST {site}/_api/site/CreateCopyJobs` з тілом:

```json
{
  "exportObjectUris": ["https://contoso.sharepoint.com/sites/spomover-test/Shared%20Documents/SpikeRun-…/…"],
  "destinationUri": "https://contoso.sharepoint.com/sites/spomover-test/SpikeTarget/SpikeRun-…",
  "options": { "IsMoveMode": true, "IgnoreVersionHistory": false, "AllowSchemaMismatch": true, "KeepBoth": false, "BypassSharedLock": false, "RetainEditorAndModifiedOnMove": true }
}
```

далі `POST {site}/_api/site/GetCopyJobProgress` з `{"copyJobInfo": <об'єкт з відповіді: JobId, JobQueueUri, EncryptionKey…>}` кожні 2–5 с, доки `JobState` = 0. Якщо SharePoint відповідає `400 The property 'X' does not exist on type 'SP.CopyMigrationOptions'`, утиліта прибирає `X`, повторює запит і записує це у звіт: так видно, які назви параметрів API справді приймає.

| Крок | Що робить | Навіщо |
|---|---|---|
| `access` | Токени Graph і SharePoint (claims `aud`, `roles` — у `raw/`); сайт і обидві бібліотеки через Graph (drive id) і REST (GUID списку, серверна адреса, кількість елементів). `401`/`403` від REST — явне повідомлення про відсутній дозвіл SharePoint `Sites.Selected`. | Підтвердити модель доступу для `SpoRestClient` (етап 4, п. 1). |
| `seed` | Папка `SpikeRun-<час>` у джерелі: «Переміщення папки» з N файлами + вкладена папка + файл зі шляхом ≈ 295 символів; «Часткове переміщення» (10 файлів); «Конфлікт», «Конфлікт папки», «Тривалість завдання», «Сканування check-out», порожня «Відкритий файл». Кирилиця і пробіли в усіх іменах. Завантаження через Graph, 4 паралельно. | Дані для інших кроків; довгі шляхи і кирилиця в URI `CreateCopyJobs`. |
| `move-folder` | Просить завантажити 1–2 власні файли в папку (щоб Автор / Ким змінено були людиною, а не застосунком). Поля Created, Author, Modified, Editor зразків до і після; переміщення папки в ціль; підрахунок файлів у цілі і джерелі; час; чи є в журналі запис про кожен файл. | EXE-1, EXE-2: формат журналу, швидкість, збереження метаданих (FEATURES 16, п. 2). |
| `partial` | Бере на check-out один файл папки, переміщує всю папку, дивиться журнал, що лишилося в джерелі і чи створено папку в цілі; потім `UndoCheckOut()`. | EXE-5 (дочищення залишків), класи `locked:checkout` і `partial` (FEATURES 9). |
| `shared-lock` | Ручна дія: завантажити свій .docx/.xlsx у папку і тримати відкритим у Word/Excel для вебу. Переміщення з `BypassSharedLock = false`; якщо файл не переміщено — ще раз з `true`. Утиліта питає, що користувач побачив у документі і чи збереглася остання зміна. | LCK-2 (`locked:shared`, відкладені хвилі), FEATURES 16, п. 3. |
| `conflict` | (а) У цілі заздалегідь файл з тим самим ім'ям, переміщення файлу з `KeepBoth = false`: помилка, перезапис чи копія. (б) У цілі вже є однойменна папка з одним однойменним файлом, переміщення папки: злиття чи помилка. | EXE-4 (перевірка конфліктів до пакета), клас `conflict:name`, розбиті пакети в наявні цільові папки (PLN-2, EXE-3). |
| `job-lifetime` | Невелике завдання, потім `GetCopyJobProgress` для нього і для всіх завершених завдань зі `state.json` через 0 с, 1, 5, 15 хв. | EXE-8: чи можна після перезапуску дізнатися результат завдання за збереженим JobId, і скільки часу. |
| `checkout-scan` | Бере файл на check-out і шукає його трьома способами: (а) Graph `delta` з `$select=…,publication` — чи є `publication.level` / `checkedOutBy`; (б) REST перелік усіх елементів `items?$select=Id,FileRef,CheckoutUserId&$orderby=Id&$top=5000` з `odata.nextLink` — чи видно `CheckoutUserId`, час на сторінку, оцінка для 1,5 млн; (в) `lists(guid'…')/GetCheckedOutFiles()` — чи працює з дозволом застосунку. Потім `UndoCheckOut()`. | INV-3 і LCK-1: як знайти файли на check-out у бібліотеці понад 5000 елементів без помилки порогу. |
| `cleanup` | Після підтвердження скасовує check-out, зроблені утилітою, і видаляє `SpikeRun-<час>` в обох бібліотеках (у кошик сайту). | Прибрати за собою. |

Не перевіряється автоматично: файл без жодної опублікованої версії (потребує бібліотеки з обов'язковим check-out — це зміна налаштувань, яку краще зробити вручну, завантажити файл і повторити `partial`) і вартість запитів у RU (SharePoint її не повертає; видно лише `RateLimit-*` поблизу ліміту).

### Додатково виявлено

- **Політика збереження на сайті.** Видалення непорожньої папки відхиляється: `403 accessDenied: Request was cancelled by event received… it's possible that it's on hold`. Файли й порожні папки видаляються. На сайті є `PreservationHoldLibrary` (441 елемент після тестів); застосунок із роллю `write` її вмісту не бачить, тож не встановлено, чи створює переміщення копії в ній. CreateCopyJobs у режимі move видаляє джерело без цієї помилки.
- **Дефект утиліти:** повторний запуск з тим самим `--out` перезаписує `report.md` (лишаються `raw/` і вивід консолі).

### Висновки для дизайну (FEATURES, IMPLEMENTATION_PLAN)

1. **Check-out — з delta, без REST**: додати `publication` у `$select` delta (INV-1) — інформація приходить разом із переліком, без окремого проходу. REST-перелік лишити запасним варіантом. Файли без опублікованої версії потребують `fullcontrol` (або не перевіряються).
2. **Пакет не можна відправляти в наявну однойменну папку** (п. 14): PLN-2 уже це передбачає — якщо цільова папка існує, переміщуються її діти.
3. **Конфлікт імен — помилка за замовчуванням** (п. 13): `KeepBoth` не потрібен; файл лишається в джерелі, що й треба для `conflict:name`.
4. **Пофайловий результат — звіркою, а не з журналу** (п. 4): після завдання — перелік цільової і джерельної папок (EXE-5). Журнал — підсумки, помилки з URL і фази.
5. **Журнал зберігати при кожному опитуванні** (п. 5); кінець завдання — `JobEnd` фази MoveCleanup, а не перше `JobState` 0.
6. **Головний ризик — швидкість** (п. 6): ≈ 1,4 с на файл у фазі Import дає тижні для 1,5 млн файлів в одному потоці. Потрібен другий прогін: 1 000 і 5 000 файлів, кілька паралельних завдань, файли реального розміру.

### Висновки після другого і третього прогонів

1. **Основний примітив — `SP.MoveCopyUtil.MoveFolderByPath`**, а не CreateCopyJobs. Він працює ≈ 6,6 файла/с на виклик, а CreateCopyJobs ≈ 1,2 файла/с на завдання. Обидва дають однакову поведінку при конфлікті (помилка, без злиття і перезапису) і зберігають поля. MoveFolderByPath синхронний: немає `jobId`, опитування й черги журналу. Результат визначається відповіддю і звіркою (EXE-5).
2. **Обмеження MoveFolderByPath — поріг подання списку**: папка, у піддереві якої понад 5 000 елементів (файлів і папок разом), відхиляється відразу (`SPQueryThrottledException`), нічого не переміщуючи. Тому ліміт пакета для нього — **за кількістю елементів піддерева, з запасом**. Пропоноване значення за замовчуванням — **1 000 елементів**: це ≈ 140 с на запит, далеко від тайм-аутів HTTP. Більші пакети (до 4 000) не перевірялися на тайм-аут.
3. **CreateCopyJobs — запасний шлях** для папок, які не можна розбити на пакети під поріг (одна папка з понад 5 000 файлів без підпапок), і для повторів. З ним працюють `NameConflictBehavior` (1 — замінити, 2 — зберегти обидва) і пофайлові `JobError`.
4. **Паралельність масштабується лінійно** для обох API: 4 і 8 завдань CreateCopyJobs, 4 виклики MoveFolderByPath. Загальну швидкість задає EXE-6 (кількість одночасних пакетів). Оцінка для 1,5 млн файлів: при 8 одночасних MoveFolderByPath (≈ 50 файлів/с) — ≈ 8–9 год чистого часу. Межу, де почнеться throttling (429/503), не досягнуто; її треба шукати на пілоті, піднімаючи паралельність поступово.
5. **Автори, яких немає на сайті**, не заважають переміщенню. Їхні ID зберігаються, а Graph не повертає для таких файлів `createdBy`. Звіти SPOMover не повинні покладатися на `createdBy` з Graph.
6. Ручні перевірки лишаються до пілоту: check-out користувачем, файл без опублікованої версії. Їх може зробити лише людина в браузері. (Файл, відкритий у Word/Excel, перевірено 09.11.2026, пп. 40–42.)
