# SPOMover — перелік функціоналу

Інструмент для контрольованого розділення великої бібліотеки SharePoint Online (1,5 млн+ файлів) на кілька бібліотек того самого сайту: папки з різних місць джерела переміщуються в задані бібліотеки і папки за таблицею мапінгу.
Форк [SPOReplaceLink](../../SPOReplaceLink): інфраструктура (підключення, throttling, база стану, повтори, хост, CLI, GUI, інсталятор) береться звідти, предметна частина пишеться заново.

Пріоритети: **MVP** — потрібне для першого бойового прогону; **P2** — бажане, другий етап; **P3** — за потреби.

Вихідні умови замовника:
- усі цільові бібліотеки на тому самому сайті, що й джерело;
- історія версій, унікальні дозволи і посилання для спільного доступу не потрібні;
- операція — переміщення (move), а не копіювання.

---

## 1. Ключові принципи

| # | Принцип | Що це означає на практиці |
|---|---|---|
| P-1 | Переміщення лише на сервері | Вміст файлів не завантажується і не вивантажується. Переміщення виконує SharePoint (Copy/Move API), інструмент лише планує, запускає і перевіряє. |
| P-2 | План до дії | Будь-яке переміщення виконується тільки за планом, побудованим з інвентаризації і мапінгу. План можна переглянути, експортувати і погодити до запуску. |
| P-3 | Детермінованість | Однакові інвентаризація і мапінг завжди дають однаковий план. Порядок рядків мапінгу не впливає на результат. |
| P-4 | Ідемпотентність | Повторний запуск не переміщує вже переміщене і не створює дублікатів. При конфлікті імен — помилка, а не «зберегти обидва». |
| P-5 | Нічого не пропускається мовчки | Кожен файл, що підпадає під мапінг, отримує фінальний статус. Файли без правила потрапляють у звіт. |
| P-6 | Відновлюваність | Після падіння, зупинки чи перезавантаження прогін продовжується з того самого місця. Запущені на сервері завдання переміщення не губляться: їхні ідентифікатори зберігаються до запуску. |
| P-7 | Безпечність за замовчуванням | Режим за замовчуванням — `plan` (dry-run). Переміщення лише в режимі `apply` з підтвердженням. |
| P-8 | Кожна невдача має наступний крок | Помилки класифікуються, тимчасові повторюються автоматично, заблоковані відкладаються, решта потрапляє в «потребують уваги» з рекомендованою дією. |
| P-9 | Навантаження під контролем | Робота в межах бюджету RU застосунку і у вікнах роботи (спадок SPOReplaceLink, розділ 11). |

## 3. Мапінг

| ID | Функція | Пріоритет |
|---|---|---|
| MAP-1 | Правило = шлях у бібліотеці-джерелі (папка або файл) → цільова бібліотека + шлях у ній. Правило для папки стосується всього її піддерева. | MVP |
| MAP-2 | Вкладені правила: для шляху діє правило з найдовшим збігом. Наприклад, `/Фін` → `Фінанси/`, а `/Фін/Архів` → `Архів/Фін`. | MVP |
| MAP-3 | Нормалізація перед порівнянням: регістр, percent-encoding (включно з кирилицею), `\` ↔ `/`, кінцевий слеш. Збіг лише на межі сегмента шляху. Береться з `Core/Urls` SPOReplaceLink. | MVP |
| MAP-4 | Валідація: дублікати; два правила, що ведуть в одну цільову папку з конфліктом імен; цільовий шлях довший за 400 символів після переміщення; недопустимі символи; неіснуюча цільова бібліотека; правило, що не збігається з жодним елементом інвентаризації. | MVP |
| MAP-5 | Звіт покриття: скільки файлів і обсягу покриває кожне правило, скільки файлів не покриває жодне (за замовчуванням вони лишаються в джерелі). | MVP |
| MAP-6 | Імпорт з CSV/XLSX (три колонки: джерело, бібліотека, цільовий шлях), експорт у CSV. Редактор у GUI з перевіркою під час введення (на основі редактора шаблонів правил). | MVP |
| MAP-7 | `map test <шлях>` — яке правило спрацює і куди потрапить елемент. | MVP |
| MAP-8 | Експорт правил для SPOReplaceLink з прогону apply: CSV `old,new,name` з абсолютними адресами. Папка, переміщена повністю, — одне правило; файли, переміщені поодинці (пакети файлів, частково переміщені папки), — правило на кожен; непереміщене правил не отримує. CLI `export-rules`. Реалізовано. | MVP |

| INV-3 | Файли на check-out з власником — з самого переліку (Graph delta, `publication.level` і `checkedOutBy`; підтверджено етапом 0). Файли без жодної опублікованої версії — окремо (SharePoint REST `GetCheckedOutFiles`, потребує `fullcontrol`): їх не видно в delta. | MVP |
| INV-4 | Інвентаризація цільових бібліотек: для виявлення конфліктів імен до запуску. | MVP |
| INV-5 | Оновлення інвентаризації за delta-токеном попередньої: новий прогін копіює її файли й папки і застосовує лише зміни (нові, змінені, перейменовані, переміщені, видалені); шляхи під перейменованими папками перераховуються звіркою з деревом папок наприкінці (працює і після перерви). Бібліотеки, яких раніше не було, перелічуються повністю. CLI `inventory --update`, галочка в діалозі нового прогону. | MVP |
| INV-6 | Звіт інвентаризації: кількість файлів і обсяг за верхніми папками, найбільші папки, найглибші шляхи, файли на check-out. | MVP |

## 5. Планування

| ID | Функція | Пріоритет |
|---|---|---|
| PLN-1 | План — набір пакетів. Пакет = одна папка цілком або набір файлів однієї папки + цільова папка. | MVP |
| PLN-2 | Правило розбиття: папка переміщується цілком, якщо її піддерево (файли і папки) вкладається в ліміт пакета (`plan.maxBatchItems`, за замовчуванням 1 000, менше порогу 5 000), у ньому немає вкладених правил з іншою ціллю, цільової папки ще немає і вона не потрібна іншому пакету. Інакше в цілі створюється папка з тим самим ім'ям, а дочірні елементи плануються окремо; файли самої папки — пакетами файлів. Файли, чий новий шлях зайнятий, не плануються (конфлікт). | MVP |
| PLN-3 | Хвилі: одна хвиля на рядок мапінгу (ручне перегрупування — з GUI, етап 5); для кожної хвилі — кількість файлів, обсяг і прогноз часу: файли ÷ (`plan.filesPerSecond` × `plan.parallel`), за замовчуванням 6,6 файла/с і 4 пакети. | MVP |
| PLN-4 | План фіксується як знімок (кожна побудова). Новий план порівнюється з попереднім планом профілю: пакети додані, прибрані, змінені (звіт `changes`, рядок у підсумку). | MVP |
| PLN-5 | Експорт плану в CSV/XLSX для погодження. | MVP |

## 6. Виконання

| ID | Функція | Пріоритет |
|---|---|---|
| EXE-1 | Переміщення пакета — SharePoint REST `SP.MoveCopyUtil.MoveFolderByPath` (папка цілком) / `MoveFileByPath` (файли пакета файлів і залишки), `KeepBoth = false`, `RetainEditorAndModifiedOnMove = true`, `ShouldBypassSharedLocks` — `move.bypassSharedLocks` профілю. Запит синхронний; час очікування — `performance.requestTimeoutSeconds` + `move.secondsPerItem` × елементів пакета. Без відповіді (таймаут, обрив, 5xx) запит не повторюється: стан визначає звірка (клас `job`). Реалізовано (етап 4); CreateCopyJobs як запасний шлях не знадобився: папку над порогом виконавець переміщує поелементно (EXE-5). | MVP |
| EXE-2 | Результат пакета: `done` (усе в цілі, піддерево джерела порожнє), `partial` (частина файлів — конфлікт, блокування понад ліміт, помилка), `deferred` (чекає заблокованих файлів), `failed:<клас>`. Статус кожного файлу — у таблиці файлів прогону (`moved`, `deferred`, `skipped:notfound`, `failed:conflict`, `failed:locked`, …). | MVP |
| EXE-3 | Створення цільових папок плану (батьківські першими) до запуску пакетів; наявна папка — не помилка. Реалізовано. | MVP |
| EXE-4 | Перевірка перед пакетом: джерело існує, у цілі немає конфлікту імен. Реалізовано як реакція на відповідь SharePoint: ціль уже є — пакет переходить на поелементне переміщення, файл з тим самим ім'ям — `failed:conflict` без перезапису. | MVP |
| EXE-5 | Після переміщення папки — перевірка, що джерела більше немає. Якщо щось лишилося (заблокований файл, понад 5 000 елементів, ціль уже існує, невідомий результат), вміст джерельної папки переміщується поелементно в ту саму ціль: файли — по одному, підпапки — цілком, де можна. Файли, яких у джерелі вже немає, звіряються з ціллю (`moved` або `skipped:notfound`). Реалізовано. | MVP |
| EXE-6 | Обмеження кількості одночасних пакетів (`plan.parallel`). Швидкість росте лінійно з паралельністю (перевірено до 8 завдань CreateCopyJobs і 4 викликів MoveFolderByPath). У межах хвилі пакети йдуть від найбільших до найменших. Стартова паралельність і її поступове збільшення до першого throttling визначаються на пілоті. | MVP |
| EXE-7 | Видалення порожніх папок у джерелі після перевірки хвилі: окремий прогін `cleanup` — лише порожні в мить перевірки, у межах правил мапінгу, у кошик сайту. **Виконано.** | P2 |
| EXE-8 | Після перезапуску пакети `in_progress` повертаються в чергу, і перша дія повторної спроби — звірка джерела і цілі, а не повторне переміщення. Так само після невідомого результату запиту. Реалізовано. | MVP |

## 9. Стан і повтори

Механізм SPOReplaceLink (база стану, атомарні переходи, повтори чотирьох рівнів, гарантія фінального статусу) зберігається. Змінюються сутності і статуси.

- Пакет: `pending → submitted(jobId) → completed | partial | failed → verified`.
- Файл: `pending → moved → verified`, а також `deferred`, `skipped:*`, `ignored`, `failed:<клас>`.

| Клас | Приклади | Автоповтор | Що далі |
|---|---|---|---|
| `transient` | Обрив мережі, 5xx, таймаут, 429 після вичерпання повторів | Так | Рівень 2 |
| `job` | Завдання переміщення завершилося без зрозумілого результату | Так, після звірки стану джерела і цілі | Рівень 2 |
| `locked:shared` | Файл відкритий на спільне редагування | Так, відкладено | Рівень 3 |
| `locked:checkout` | Файл на check-out | Ні | Потребує уваги (LCK-3) |
| `conflict:name` | У цілі вже є елемент з таким ім'ям | Ні | Потребує уваги: рішення вручну |
| `path` | Задовгий шлях, недопустимі символи | Ні | Потребує уваги: зміна мапінгу |
| `notfound` | Елемент зник з джерела до переміщення | — | `skipped:notfound` |
| `auth` | 401/403 | Ні | Запобіжник як у SPOReplaceLink |
| `internal` | Помилка в самому інструменті | Ні | Потребує уваги, повний stack trace у журналі |

## 11. Керування навантаженням

Без змін від SPOReplaceLink (бюджет RU, реакція на 429/503, вікна роботи, добовий бюджет, виявлення блокування). Додається:

| ID | Функція | Пріоритет |
|---|---|---|
| THR-12 | SharePoint REST-запити проходять через той самий бюджет RU і стан throttling, що й Graph. | MVP |
| THR-13 | Вартість `CreateCopyJobs` і навантаження від серверного переміщення вимірюються на пілоті і заносяться в таблицю вартості. | MVP |

Пул застосунків лишається в коді, але за замовчуванням вимкнений: для одного сайту він не потрібен.

## 15. Поза межами

- Переміщення між сайтами (P3: той самий API, але інші ліміти і поведінка).
- Збереження унікальних дозволів, посилань для спільного доступу, історії версій.
- Оновлення посилань усередині файлів — це робить SPOReplaceLink за правилами з MAP-8.
- Оновлення вкладок Teams, потоків Power Automate, ярликів OneDrive.

## 16. Відкриті питання

1. Скільки файлів у найбільших папках і яка максимальна глибина — з першої інвентаризації.
2. Чи потрібно зберігати «Ким змінено» і «Змінено» (`RetainEditorAndModifiedOnMove`).
3. Як поводиться `BypassSharedLock` для користувача, у якого файл відкритий, — перевірити на пілоті.
4. Що робити з файлами на check-out, якщо власник не відповідає: check-in, скасування чи пропуск.
5. Чи синхронізують користувачі бібліотеку через OneDrive (потрібна розсилка до старту).
